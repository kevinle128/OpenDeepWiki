# Docker 部署

本指南涵盖了超出 [快速开始](/docs/getting-started) 范围的高级 Docker 部署场景。

## Docker Compose 概览

项目根目录的 `compose.yaml` 定义了两个服务：

| 服务 | 容器端口 | 默认宿主机映射 | 描述 |
|---|---|---|---|
| `opendeepwiki` | `8080` | `18081` | 带有 AI 处理的 ASP.NET Core API |
| `web` | `3000` | `8090` | Next.js 前端应用 |

`compose.pgsql.yaml` 使用 `8080` 和 `3000`，并增加 `postgres` 服务。前端通过内部网络的 `API_PROXY_URL=http://opendeepwiki:8080` 访问后端。两个 compose 文件都要求设置 `JWT_SECRET_KEY`（至少 32 字节的随机值），否则 `docker compose` 报错并拒绝启动。

## 构建镜像

### 构建所有镜像

```bash
docker compose build
```

### 特定架构构建

通过 Makefile 为特定 CPU 架构构建：

```bash
# ARM64（Apple Silicon、AWS Graviton 等）
make build-arm

# AMD64（Intel/AMD x86_64）
make build-amd
```

### 构建单个服务

```bash
# 仅后端
docker compose build opendeepwiki

# 仅前端
docker compose build web
```

## 生产环境运行

### 后台启动

```bash
docker compose up -d
```

### 查看日志

```bash
docker compose logs -f
```

### 停止服务

```bash
docker compose down
```

## 数据持久化

后端将数据存储在映射到 `./data` 的 Docker 卷中：

```yaml
volumes:
  - ./data:/data
```

此目录包含：
- SQLite 数据库文件（如果使用 SQLite）
- 用于分析的克隆仓库文件
- Data Protection 密钥环 `./data/dataprotection-keys`，用来解密已保存的 Git 连接令牌

<Callout type="warn">
  在生产环境中定期备份 `./data` 目录。它包含所有生成的文档和仓库数据。数据库和密钥环必须一起备份、一起恢复：
  丢失密钥环后，所有已保存的 Git 连接令牌都无法读取，必须在工作区中重新输入。
  备份、升级步骤和冒烟检查见 [Docker Compose 部署](/docs/deployment/docker-compose#git-connection-secrets)。
</Callout>

## 健康检查

后端包含内置的健康检查端点 `/health`（`compose.yaml` 和 `compose.pgsql.yaml` 中都已配置容器健康检查，`web` 在后端健康后才启动）：

```yaml
healthcheck:
  test: ["CMD-SHELL", "curl -f http://localhost:8080/health || exit 1"]
  interval: 30s
  timeout: 10s
  retries: 3
  start_period: 15s
```

## 升级后的冒烟检查

升级前先备份数据库和密钥环。升级后运行：

```bash
docker compose ps                          # opendeepwiki 为 healthy
curl --fail http://localhost:18081/health  # compose.pgsql.yaml 使用 8080
curl --fail http://localhost:8090/         # compose.pgsql.yaml 使用 3000
```

升级后的第一次启动会改用 `JWT_SECRET_KEY` 签名，所有用户需要重新登录一次。后端的致命启动错误（例如 Production 环境缺少密钥环路径）会以退出码 1 结束进程，原因在 `docker compose logs opendeepwiki` 中。如果旧版本把私有仓库的密码明文保存在数据库中，见 [旧凭据迁移](/docs/deployment/legacy-credential-migration)。

## 数据库配置

### SQLite（默认）

无需额外设置。数据库文件会自动创建：

```yaml
environment:
  - DB_TYPE=sqlite
  - CONNECTION_STRING=Data Source=/data/opendeepwiki.db
```

### PostgreSQL

对于生产工作负载，推荐使用 PostgreSQL。仓库自带 PostgreSQL 编排文件：

```bash
docker compose -f compose.pgsql.yaml up -d --build
```

详见 [数据库配置](/docs/deployment/database)。

## AI 提供商配置

OpenDeepWiki 为不同任务使用独立的 AI 配置：

| 配置组 | 用途 | 关键变量 |
|---|---|---|
| 聊天 | 对话式 AI 功能 | `CHAT_API_KEY`、`ENDPOINT`、`CHAT_REQUEST_TYPE` |
| Wiki 目录 | 生成文档结构 | `WIKI_CATALOG_MODEL`、`WIKI_CATALOG_ENDPOINT`、`WIKI_CATALOG_API_KEY` |
| Wiki 内容 | 生成文档内容 | `WIKI_CONTENT_MODEL`、`WIKI_CONTENT_ENDPOINT`、`WIKI_CONTENT_API_KEY` |
| 翻译（可选） | 翻译文档 | `WIKI_TRANSLATION_*`（未设置时回退到内容配置） |

所有配置组都可以指向同一提供商，或者为每个任务使用不同的模型/提供商。管理员也可在后台「模型管理」中绑定 Provider/Model。

详见 [AI 提供商](/docs/deployment/ai-providers)。

## Graphify 图谱产物（可选）

后端 Docker 镜像已内置 `graphifyy` CLI。在 `compose.yaml` 中补充以下可选变量即可启用知识图谱产物生成：

- `GRAPHIFY_BACKEND`
- `GRAPHIFY_MODEL`
- `GRAPHIFY_OPENAI_BASE_URL` / `GRAPHIFY_OPENAI_API_KEY`
- `OPENAI_BASE_URL` / `OPENAI_API_KEY`
- `OLLAMA_BASE_URL` / `OLLAMA_MODEL`

产物输出到 `GRAPHIFY_OUTPUT_ROOT`（默认 `/data/graphify-artifacts`），在前端仓库页的 `/graphify` 路由查看。

## 故障排除

### 后端启动失败

- 检查 AI API 密钥是否有效且端点可达
- 验证 `CONNECTION_STRING` 对你的数据库类型是否正确
- 查看日志：`docker compose logs opendeepwiki`

### 前端显示连接错误

- 确保后端已启动：`docker compose ps`
- `web` 服务中的 `API_PROXY_URL` 应指向后端容器：`http://opendeepwiki:8080`

### 磁盘空间不足

- 克隆的仓库存储在 `./data` 中。通过 web UI 或 API 清理旧仓库
- 如果使用 SQLite，数据库文件会随时间增长。对于大型部署，考虑切换到 PostgreSQL

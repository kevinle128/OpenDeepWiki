## 概览

OpenDeepWiki 后端是一个 ASP.NET Core 应用，目标是 .NET 10，位于 `src/OpenDeepWiki/`。它使用最小 API 进行端点路由，Entity Framework Core 进行数据访问，并与多个 AI 提供商集成以实现 wiki 生成和聊天功能。

## 最小 API 端点

后端使用 ASP.NET Core 最小 API，路由组按域组织。每个端点文件定义一个静态扩展方法来注册路由：

```csharp
public static class ChatAssistantEndpoints
{
    public static IEndpointRouteBuilder MapChatAssistantEndpoints(
        this IEndpointRouteBuilder app)
    {
        var group = app.MapGroup("/api/v1/chat")
            .WithTags("Chat Assistant");

        group.MapGet("/config", GetChatConfigAsync);
        group.MapGet("/models", GetAvailableModelsAsync);
        group.MapPost("/stream", StreamChatAsync);

        return app;
    }
}
```

所有端点在 `Program.cs` 中注册：

```csharp
app.MapMiniApis();                    // [MiniApi] 标注的服务方法自动映射
app.MapRepositoryUploadEndpoints();
app.MapAuthEndpoints();
app.MapApiKeyEndpoints();
app.MapOAuthEndpoints();
app.MapAdminEndpoints();
app.MapGitHubImportEndpoints();
app.MapOrganizationEndpoints();
app.MapChatAssistantEndpoints();
app.MapChatAppEndpoints();
app.MapEmbedEndpoints();
app.MapSystemEndpoints();
app.MapIncrementalUpdateEndpoints();
app.MapBranchGenerationEndpoints();
app.MapGitConnectionEndpoints();
app.MapConnectedRepositoryEndpoints();
app.MapMcpProviderEndpoints();
// ...
```

MCP 端点单独注册，支持按路径限定仓库范围（详见 [MCP 协议](/docs/mcp)）：

```csharp
app.MapMcp("/api/mcp");
app.MapMcp("/api/mcp/{owner}/{repo}");
```

## Shared Git connections

A Git connection holds one provider token for one provider account. Every signed-in user can use it. Only the creator
and an Admin can change it. The API is described in [Repositories API](/docs/api-reference/repositories). This section
describes the parts of the backend that make it safe.

### Provider clients

`IGitProviderClient` has one implementation for each provider: `GitHubPatProviderClient` (GitHub, with
`https://github.com` as the only origin) and `GitLabPatProviderClient` (GitLab.com or a self-hosted GitLab).
`IGitProviderClientResolver` selects the client by `GitProvider`.

- Repositories and branches are addressed by the numeric provider ID, so a rename or a transfer does not break a link.
- Lists use cursor paging. The cursor is opaque. `ProviderPaginationCursorCodec` protects it with Data Protection and
  binds it to the provider, the connection, and the API origin, so a cursor from one connection is refused on another.
  The backend never follows a pagination link from the provider.
- Every failure becomes a `GitProviderException` with a stable code (`PROVIDER_*`). Messages never contain provider text
  or the token. A rejected token returns HTTP 422 (not 401, because the web client signs the user out on any 401).
  Rate limits return 429 with `Retry-After`, timeouts 504, and other provider failures 502.
- Tokens travel only in request headers. Automatic redirects are off, so a redirect target never receives the token.

### Address policy

`GitLabServerUrlValidator` accepts only an HTTPS origin and resolves the host name once. `GitProviderGuardHandler` runs
in front of the GitLab handler, and the handler connects only to the validated addresses, so the check and the
connection use the same DNS answer. Public addresses pass. Private and loopback addresses need an entry in
`GitProviders:AllowedPrivateHosts` or `GitProviders:AllowedPrivateCidrs`. Link-local, metadata, unspecified, multicast,
and reserved addresses are always blocked. See [Environment variables](/docs/configuration/environment-variables).

### Token protection

`DataProtectionGitConnectionSecretProtector` encrypts the token before it is stored in `GitConnections.ProtectedToken`.
The key ring is in `DataProtection:KeyRingPath` and is required in Production (`Program.ValidateProductionSecurity`).
No API returns a token. Code decrypts it only to call the provider or to run a Git operation, and `GitCredentialResolver` selects the credential for each Git operation. A repository that has a
`GitConnectionId` uses its connection only: when the connection is disabled, deleted, or unreadable, the operation
fails and never falls back to the old password. A repository without a connection uses the legacy fields.

During clone and fetch, `RepositoryAnalyzer` gives the credential only to the origin stored on the connection. The
remote must be an HTTPS URL without user information and must pass the address policy before the credential is read. No
certificate check bypass is installed.

### Authorization

| Action | Who can do it |
|---|---|
| Create a connection, list connections, browse the catalog, connect a repository, add and remove branches, rebuild, sync, retry, cancel | Any signed-in user (anonymous: 401) |
| Rename, rotate the token, test, enable, disable, delete, read audit events | The creator or an Admin (other users: 403 `CONNECTION_MAINTENANCE_FORBIDDEN`) |
| Delete a repository, change its visibility | Unchanged: Admin policy and the owner rule |
| Read or change a private repository | Its owner or an Admin. Other users get 404. There is no department rule |

`IGitConnectionAuthorizationService` decides `CanUse` and `CanMaintainAsync`. Branch routes need a signed-in user and check that
the branch belongs to the repository in the URL.

### Orchestration

- `ConnectedRepositoryService` connects a repository to a connection. It checks every selected branch against the
  provider, then writes the repository, the branches, one full-generation task for each new branch, one branch lock for
  each task, and the audit events in one transaction. The first statement of the transaction touches the connection row
  only if the connection is enabled and not deleted, so a connection that is disabled or deleted at that moment is
  rejected. A repeated request changes nothing. A new connected repository starts with the status `Completed` and
  its branches carry the tasks.
- `RepositoryGenerationLockService` has repository-scope locks and branch-scope locks. Two branches of one repository can
  run at the same time and still share the global generation slots. A repository-scope lock excludes every other lock
  of that repository.
- `BranchGenerationTaskService` queues, retries, and cancels full-generation tasks for one branch. Each task is
  independent: another branch of the same repository is not changed.
- `IndexedBranchRemovalService` removes one branch with its catalogs, documents, languages, tasks, locks, and
  artifacts in one transaction. If a task of that branch is processing, it returns 409 `BRANCH_JOB_ACTIVE` and changes
  nothing. `BranchGenerationWorker` removes the workspace directories of removed branches every five minutes.
- `BranchActionAuditor` writes who did what (`BranchAdded`, `BranchRebuildRequested`, `BranchSyncRequested`,
  `BranchTaskRetried`, `BranchTaskCancelled`, `BranchRemoved`) to `GitConnectionAuditEvents`.

Automatic synchronisation is not a per-repository setting. `IncrementalUpdateWorker` runs one global schedule
(`IncrementalUpdate:*`), and a user can start a sync of one branch by hand.

### Legacy credential migration

`LegacyGitCredentialMigrationService` moves old plaintext credentials into connections. An Admin starts it through
`/api/admin/git-connection-migration`. Nothing runs at start-up. Removing the legacy columns is written and tested on
copies, and it is not active. The runbook is [Legacy credential migration](/docs/deployment/legacy-credential-migration).

## AI 集成（AgentFactory）

`AgentFactory` 是创建 AI 客户端的中央抽象，基于 `Microsoft.Agents.AI` 构建。它通过统一接口支持多个提供商：

```csharp
public enum AiRequestType
{
    OpenAI,
    AzureOpenAI,
    OpenAIResponses,
    Anthropic,
    DeepSeekOpenAI
}
```

工厂创建配置了适当提供商、端点和 API 密钥的 `ChatClientAgent` 实例，并在 HTTP 管道中串联 `FinishReasonNormalizingHandler -> LoggingHttpHandler -> HttpClientHandler`（归一化 Gemini 等非标准 finish_reason 并记录请求日志）。Wiki 生成为不同任务使用单独的模型配置：

- **目录模型** — 生成文档结构/大纲（可使用更快、更便宜的模型）
- **内容模型** — 生成实际文档内容（受益于更强大的模型）
- **翻译模型** — 将文档翻译为其他语言（可选，回退到内容模型）

配置通过环境变量完成：

```
WIKI_CATALOG_MODEL, WIKI_CATALOG_ENDPOINT, WIKI_CATALOG_API_KEY
WIKI_CONTENT_MODEL, WIKI_CONTENT_ENDPOINT, WIKI_CONTENT_API_KEY
WIKI_TRANSLATION_MODEL, WIKI_TRANSLATION_ENDPOINT, WIKI_TRANSLATION_API_KEY
```

管理员也可以在后台「模型管理」中配置 Provider/Model 绑定（存于 `ModelConfig` 实体），系统设置中的绑定优先于环境变量默认值。

## 后台工作者

长时间运行的任务由 `BackgroundService` 后台工作者处理，均在 `Program.cs` 中注册：

| 工作者 | 描述 |
|--------|-------------|
| `RepositoryProcessingWorker` | 处理排队的仓库分析准备任务（克隆/解压/工作区准备） |
| `BranchGenerationWorker` | 处理分支级 Wiki 生成任务（目录 + 内容） |
| `TranslationWorker` | 处理文档翻译任务 |
| `MindMapWorker` | 为仓库分支生成思维导图内容（30 秒轮询，启动时恢复孤儿 Processing 记录） |
| `GraphifyArtifactWorker` | 生成 Graphify 图谱产物 |
| `IncrementalUpdateWorker` | 定期检查和处理增量更新 |
| `McpOAuthCleanupService` | 清理过期的 MCP OAuth 令牌 |
| `McpStatisticsAggregationService` | 聚合 MCP 使用统计 |

工作者独立运行，使用 `IServiceScopeFactory` 为每个操作创建作用域数据库上下文。

## Entity Framework Core

数据层使用共享 `MasterDbContext` 基类和 `IContext` 接口：

```csharp
public interface IContext : IDisposable
{
    DbSet<Repository> Repositories { get; set; }
    DbSet<RepositoryBranch> RepositoryBranches { get; set; }
    DbSet<DocCatalog> DocCatalogs { get; set; }
    DbSet<DocFile> DocFiles { get; set; }
    DbSet<User> Users { get; set; }
    // ... 20+ 个实体集
    Task<int> SaveChangesAsync(CancellationToken cancellationToken = default);
}
```

数据库提供商在启动时通过 `DB_TYPE` 环境变量选择：

- `sqlite` — 使用 `SqliteDbContext`（默认，基于文件）
- `postgresql` — 使用 `PostgresqlDbContext`

## 认证

后端使用 JWT Bearer 认证：

- 通过 `IJwtService` 进行令牌生成和验证
- 通过 `IUserContext` 进行用户上下文提取
- 通过 `[RequireAuthorization]` 和角色检查进行仅管理员策略
- 第三方登录提供商的 OAuth 集成（GitHub、Gitee）

## Chat 系统

OpenDeepWiki 包含一个完整的多平台聊天系统，支持通过 Webhook 接入多种即时通讯平台：

### 支持的平台

| 平台 | Webhook 端点 | 描述 |
|------|-------------|------|
| 飞书 | `POST /api/chat/webhook/feishu` | 飞书机器人消息 |
| QQ | `POST /api/chat/webhook/qq` | QQ 机器人消息 |
| 微信 | `POST /api/chat/webhook/wechat` | 微信客服消息 |
| Slack | `POST /api/chat/webhook/slack` | Slack 机器人消息 |

### 架构组件

- **Providers** — 各平台的消息处理实现（飞书、QQ、微信、Slack），继承 `BaseMessageProvider`
- **Config** — 配置加载、AES 加密存储、变更通知与热重载
- **Queue** — 消息队列系统，支持异步处理
- **Sessions** — 会话管理，维护用户对话上下文
- **Routing** — 提供商路由逻辑，根据平台分发消息
- **Execution** — `AgentExecutor` 流式执行 AI 代理并核算 Token 用量

### Provider 管理

管理员可以通过 `/api/chat/admin/providers` 端点管理各平台的 Provider 配置，包括启用/禁用、配置更新和热重载。

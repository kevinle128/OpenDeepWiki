# Legacy credential migration

Older versions stored the account and the password or token of a private repository in plaintext in the
`Repositories` table (`AuthAccount`, `AuthPassword`). Current versions keep one protected token per Git account in a
shared Git connection and let each repository point to it with `GitConnectionId`.

The move has four releases. Each one is a separate gate.

| Step | What it does | State in this release |
|---|---|---|
| Expand | Adds the progress table and the connection-first credential path. Stops every new write to the legacy fields. | Shipped |
| Backfill | An Admin starts it. It moves each legacy credential into a connection. | Shipped |
| Switch | You confirm that every repository that can move uses a verified connection. | Operator step |
| Contract | Removes the legacy fields and drops the two columns. | **Written and tested on copies. Not active.** |

<Callout type="warn">
  The legacy columns stay in the model, the schema, and `DbInitializer` in this release. Do not run the contract step
  from this page until every condition in [Contract gate](#contract-gate) is true.
</Callout>

## Before you start

1. Back up the database. For SQLite use the online backup, not a file copy, because the file can be in WAL mode:
   `sqlite3 data/opendeepwiki.db ".backup '/backups/pre-migration.db'"`. For PostgreSQL use `pg_dump`.
2. Back up the Data Protection key ring directory (`DataProtection:KeyRingPath`). A connection token can only be
   decrypted with the key ring that protected it. The database and the key ring must be restored together.
3. Restore both backups into a test environment and read one connection credential there. A restore of the database
   without its key ring must fail, and a restore of both must work.
4. Record the number of active repositories and the number that hold a legacy credential. The dry run shows both.

## Backfill

All routes are under `/api/admin/git-connection-migration`. They need the `Admin` role in the token and a current Admin
role in the database. Nothing runs at application startup, and the application never calls GitHub or GitLab for this
by itself.

| Route | Purpose |
|---|---|
| `GET /dry-run` | Counts by provider, state, and error code. Writes nothing and calls no provider. |
| `POST /migrate` with `{ "batchSize": 50 }` | Handles the next repositories that have no stored result (1 to 200). Repeat while `hasMore` is true. |
| `GET /status` | The same counts, plus the repair queue and the migration part of the contract gate. |
| `POST /retry` with `{ "repositoryIds": ["..."] }` | Runs the named repositories again (1 to 200). Migrated repositories are skipped. |

Answers contain repository IDs, connection IDs, counts, and stable codes only. They never contain a token, a Git URL, or
provider response text.

What the backfill does for one repository:

1. It infers the provider from the host. Only `github.com` and `gitlab.com` over HTTPS can be inferred. A token is
   never sent to any other host.
2. It sends the token to the provider and reads the account ID. The provider answer decides the identity, never the
   repository owner or the token text.
3. It looks for a connection with the same provider, server, and account ID. An existing connection is reused as it is:
   its creator and its credential do not change. If none exists, it creates one. Its creator is the owner of the
   earliest repository (by creation time, then ID) of that account that the run handles.
4. It links the repository through the connected repository service, which sets `GitConnectionId`, `Provider`, and
   `ProviderBaseUrl`, and writes one `RepositoryAssigned` audit event.
5. It checks the new path: the credential resolver must return the connection credential, and the repository URL must
   match the stored origin. Only then does it store `Migrated`.

The legacy fields are never changed or cleared. A rerun does not create a second connection, audit event, or link.

### States and codes

| State | Meaning |
|---|---|
| `Pending` | Not handled yet. |
| `Migrated` | Verified through the connection path. |
| `Failed` | A temporary problem: `PROVIDER_RATE_LIMITED`, `PROVIDER_UNAVAILABLE`, `PROVIDER_TIMEOUT`, `PROVIDER_DNS_FAILURE`, `UNEXPECTED_ERROR`, `VERIFICATION_FAILED`, `EARLIER_REPOSITORY_PENDING`. Use `retry` later. `EARLIER_REPOSITORY_PENDING` means an older repository of the same provider and server still waits for a retry. Retry both together: the older one runs first and its owner creates the connection. |
| `Blocked` | An Admin must repair it. |

| Blocked code | Action |
|---|---|
| `PROVIDER_UNAUTHORIZED`, `PROVIDER_FORBIDDEN` | The token is revoked or too weak. Create a connection with a valid token, then assign the repository (admin update with `gitConnectionId`). |
| `UNSUPPORTED_HOST` | Gitee, a self-hosted server, or a non-HTTPS URL. These stay as legacy repositories and block the contract step. |
| `URL_CONTAINS_USERINFO` | The Git URL holds a user name or token. Replace the URL with a clean one and assign a connection. |
| `LEGACY_CREDENTIAL_INCOMPLETE`, `LEGACY_CREDENTIAL_INVALID` | The account has no password, or the password has spaces or control characters. |
| `CONNECTION_DELETED` | The account matches a deleted connection. Restoring a shared credential needs a person: create the connection again with a valid token, then retry. |
| `CONNECTION_DISABLED`, `CONNECTION_SECRET_UNREADABLE`, `CONNECTION_NOT_FOUND` | Fix the connection (enable it, rotate its token), then retry. |
| `REMOTE_ORIGIN_MISMATCH` | The repository URL is not on the connection server. |

## Switch

New submit and admin update requests no longer write the legacy fields. A submit with `authAccount`, `authPassword`, or a
URL with user info returns 400 with a stable code (`LEGACY_CREDENTIAL_FIELDS_REJECTED`, `GIT_URL_CONTAINS_CREDENTIALS`)
and asks the caller to send `gitConnectionId`. A web form that still sends the old fields for private repositories
fails until it sends `gitConnectionId`.

The credential resolver is the only place that reads the legacy fields. A repository that has `GitConnectionId` uses its
connection only. If the connection is disabled, deleted, or unreadable the Git operation fails; it never falls back to
the legacy password. The legacy fields are used only when `GitConnectionId` is null, and each such use writes a log line
with the repository ID.

After the backfill, run `GET /status` and one full scheduled update cycle. Check clone, pull, branch list, incremental
update, and rebuild for repositories that use a connection.

## Contract gate

All of these must be true before you ship the contract release:

- `GET /status` shows `contractGateClear: true`. This means no active repository has an unmigrated legacy credential,
  an unsupported legacy host with a credential, or a credential in its URL.
- A verified database backup and a verified key ring backup exist, and the joint restore was tested.
- One full scheduled update cycle ran on connection credentials.
- No Gitee or unknown-host repository depends on the legacy columns.

<Callout type="warn">
  The gate checks only repositories that are not soft-deleted. A soft-deleted repository that still holds a legacy
  credential is not reported, and that credential is lost when the contract release runs. Restore such a repository
  and migrate it, or confirm that it is not needed, before you ship the contract release.
</Callout>

## Contract release (not active)

The contract release removes the legacy fields. It is a separate deployment. After it, an older binary cannot run
against the database, because it needs the dropped columns. Rollback is a restore of the pre-contract database and the
matching key ring, followed by the older binary.

Steps for the contract release:

1. Remove `AuthAccount` and `AuthPassword` from the `Repository` entity, the submit and admin update DTOs, the
   repository and admin services, and the resolver fallback. Delete the legacy path of `GitCredentialResolver` and
   `HasStoredCredential`. After this, `rg "AuthAccount|AuthPassword" src --glob '*.cs' --glob '!**/Migrations/*'` must
   return nothing.
2. In both `*_RemoveLegacyRepositoryCredentials.Designer.cs` files, turn the `[Migration(...)]` attribute back on.
   Replace both model snapshots with the `BuildTargetModel` content of these designers (the snapshot must lose the two
   columns). Check with `dotnet ef migrations has-pending-model-changes` for both providers; it must report no changes.
3. For databases that `DbInitializer` upgrades (no EF migration history), the release calls
   `DbInitializer.ApplyLegacyCredentialContractAsync` once, after the expand steps. It is idempotent, it refuses to run
   while an active repository still depends on a legacy credential or holds one in its URL, and it does nothing when the
   columns are gone.
   - PostgreSQL: `ALTER TABLE "Repositories" DROP COLUMN IF EXISTS` for both columns, in one transaction.
   - SQLite: the `Repositories` table is rebuilt in one transaction with foreign keys off. The new table is created from
     the stored table definition without the two columns, rows are copied by column name, the old table is dropped, the
     new one is renamed, and every index and trigger is created again. The rebuild fails if the row count changes or if
     `foreign_key_check` finds a violation.
4. Verify on the live database: row counts of every table, `PRAGMA integrity_check` is `ok`,
   `PRAGMA foreign_key_check` returns no rows, the index list of `Repositories` is unchanged, and a read-only Git
   operation on a connection repository works.

## Recovery drill

Run this before the backfill and before the contract release.

1. Restore the database backup without the key ring. A read of a connection credential must fail with
   `connection_secret_unreadable`, and no legacy password is used.
2. Restore the database backup together with the key ring backup. A read-only Git operation (for example a remote
   branch list) must work.
3. For the contract release, restore the pre-contract backup and start the older binary. The legacy columns and their
   values must be back.

## Limits

- Self-hosted GitLab repositories cannot be migrated by the backfill. The host cannot be inferred safely from a URL.
  Create the connection first, then assign the repository with an admin update.
- Gitee repositories have no connection type. They keep their legacy credential and block the contract step.
- The creator of a new connection is the owner of the earliest repository of the account. A later repository does not
  create the connection while an earlier repository of the same provider and server is still `Failed`.

# Docker Compose 部署

OpenDeepWiki 在项目根目录提供 `compose.yaml`，定义了两个服务：后端 API 和前端 web 应用。PostgreSQL 用户可直接使用 `compose.pgsql.yaml`。

## 服务架构

| 服务 | 容器端口 | 默认宿主机映射 | 描述 |
|---|---|---|---|
| `opendeepwiki` | `8080` | `18081:8080` | 带有 AI 处理的 ASP.NET Core 后端 API |
| `web` | `3000` | `8090:3000` | Next.js 前端应用 |

> 端口映射以仓库中 `compose.yaml` 的实际内容为准，可按需修改。`compose.pgsql.yaml` 使用 `8080:8080` 和 `3000:3000`，并增加 `postgres` 服务。前端通过内部网络使用 `API_PROXY_URL=http://opendeepwiki:8080` 访问后端。

## 快速部署

```bash
# 克隆仓库
git clone https://github.com/AIDotNet/OpenDeepWiki.git
cd OpenDeepWiki

# 必须设置 JWT_SECRET_KEY（至少 32 字节的随机值），否则 compose 拒绝启动
cp .env.example .env
# 编辑 .env，然后启动所有服务
docker compose up -d
```

在 `http://localhost:8090` 访问应用。

## 完整 compose.yaml 参考

以下是当前 `compose.yaml` 的关键结构（完整内容以文件为准）：

```yaml
services:
  opendeepwiki:
    image: crpi-j9ha7sxwhatgtvj4.cn-shenzhen.personal.cr.aliyuncs.com/open-deepwiki/opendeepwiki
    build:
      context: .
      dockerfile: src/OpenDeepWiki/Dockerfile
    ports:
      - "18081:8080"
    restart: unless-stopped
    user: "0:0"
    healthcheck:
      test: ["CMD-SHELL", "curl -f http://localhost:8080/health || exit 1"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 15s
    environment:
      - ASPNETCORE_ENVIRONMENT=Production
      - URLS=http://+:8080

      # 数据库
      - Database__Type=${DB_TYPE:-sqlite}
      - ConnectionStrings__Default=${CONNECTION_STRING:-Data Source=/data/opendeepwiki.db}

      # JWT（必填：至少 32 字节；Production 环境不接受内置默认值）
      - JWT_SECRET_KEY=${JWT_SECRET_KEY:?Set JWT_SECRET_KEY to a random value of at least 32 bytes}

      # Data Protection 密钥环（必须持久化，请与数据库一同备份）
      - DataProtection__KeyRingPath=/data/dataprotection-keys

      # 仓库存储与本地目录导入白名单
      - REPOSITORIES_DIRECTORY=/data
      - RepositoryAnalyzer__AllowedLocalPathRoots__0=${LOCAL_IMPORT_ROOT:-/host/home/youruser}

      # AI 服务（聊天）
      - CHAT_API_KEY=${CHAT_API_KEY:-your-chat-api-key}
      - ENDPOINT=${ENDPOINT:-https://api.openai.com/v1}
      - CHAT_REQUEST_TYPE=${CHAT_REQUEST_TYPE:-OpenAI}

      # Wiki 目录生成
      - WIKI_CATALOG_MODEL=${WIKI_CATALOG_MODEL:-gpt-4o}
      - WIKI_CATALOG_ENDPOINT=${WIKI_CATALOG_ENDPOINT:-https://api.openai.com/v1}
      - WIKI_CATALOG_API_KEY=${WIKI_CATALOG_API_KEY:-your-catalog-api-key}
      - WIKI_CATALOG_REQUEST_TYPE=${WIKI_CATALOG_REQUEST_TYPE:-OpenAI}

      # Wiki 内容生成
      - WIKI_CONTENT_MODEL=${WIKI_CONTENT_MODEL:-gpt-4o}
      - WIKI_CONTENT_ENDPOINT=${WIKI_CONTENT_ENDPOINT:-https://api.openai.com/v1}
      - WIKI_CONTENT_API_KEY=${WIKI_CONTENT_API_KEY:-your-content-api-key}
      - WIKI_CONTENT_REQUEST_TYPE=${WIKI_CONTENT_REQUEST_TYPE:-OpenAI}

      # Wiki 翻译（可选，回退到内容配置）
      # - WIKI_TRANSLATION_MODEL=gpt-4o
      # - WIKI_TRANSLATION_ENDPOINT=https://api.openai.com/v1
      # - WIKI_TRANSLATION_API_KEY=your-api-key
      # - WIKI_TRANSLATION_REQUEST_TYPE=OpenAI

      # 并行生成数量 / 多语言支持
      - WIKI_PARALLEL_COUNT=${WIKI_PARALLEL_COUNT:-5}
      - WIKI_MAX_CONCURRENT_GENERATIONS=${WIKI_MAX_CONCURRENT_GENERATIONS:-1}
      - WIKI_LANGUAGES=${WIKI_LANGUAGES:-en,zh,zh-tw,ja,ko,es,fr,de,pt-br,pl,ru,ar}

      # Graphify 图谱产物（可选）
      - GRAPHIFY_BACKEND=${GRAPHIFY_BACKEND:-}
      - GRAPHIFY_MODEL=${GRAPHIFY_MODEL:-}
      - GRAPHIFY_OUTPUT_ROOT=/data/graphify-artifacts
      - GRAPHIFY_OPENAI_BASE_URL=${GRAPHIFY_OPENAI_BASE_URL:-}
      - GRAPHIFY_OPENAI_API_KEY=${GRAPHIFY_OPENAI_API_KEY:-}
    volumes:
      - ./data:/data

  web:
    image: crpi-j9ha7sxwhatgtvj4.cn-shenzhen.personal.cr.aliyuncs.com/open-deepwiki/opendeepwiki-web
    build:
      context: ./web
      dockerfile: Dockerfile
    ports:
      - "8090:3000"
    restart: unless-stopped
    depends_on:
      opendeepwiki:
        condition: service_healthy
    environment:
      - NODE_ENV=production
      - SITE_URL=${SITE_URL:-http://localhost:8090}
      - API_PROXY_URL=http://opendeepwiki:8080
```

<Callout type="info">
  根目录提供 `.env.example`，可复制为 `.env` 后通过 `${VAR:-default}` 插值注入配置，无需直接修改 `compose.yaml`。
</Callout>

## 环境变量

### 必需变量

| 变量 | 描述 | 示例 |
|---|---|---|
| `JWT_SECRET_KEY` | JWT 签名密钥。至少 32 个 UTF-8 字节，不得为内置默认值。两个 compose 文件都要求设置它，未设置时 `docker compose` 报错并拒绝启动 | 长随机字符串 |
| `CHAT_API_KEY` | 聊天 AI 服务的 API 密钥 | `sk-...` |
| `ENDPOINT` | 聊天 AI 服务端点 | `https://api.openai.com/v1` |
| `WIKI_CATALOG_API_KEY` | 目录生成的 API 密钥 | `sk-...` |
| `WIKI_CATALOG_ENDPOINT` | 目录生成端点 | `https://api.openai.com/v1` |
| `WIKI_CONTENT_API_KEY` | 内容生成的 API 密钥 | `sk-...` |
| `WIKI_CONTENT_ENDPOINT` | 内容生成端点 | `https://api.openai.com/v1` |

### 可选变量

| 变量 | 默认值 | 描述 |
|---|---|---|
| `DB_TYPE` | `sqlite` | 数据库类型：`sqlite` 或 `postgresql` |
| `CONNECTION_STRING` | `Data Source=/data/opendeepwiki.db` | 数据库连接字符串 |
| `WIKI_CATALOG_MODEL` | `gpt-4o` | 目录生成模型 |
| `WIKI_CONTENT_MODEL` | `gpt-4o` | 内容生成模型 |
| `CHAT_REQUEST_TYPE` | `OpenAI` | AI 提供商类型：`OpenAI`、`AzureOpenAI`、`OpenAIResponses`、`Anthropic`、`DeepSeekOpenAI` |
| `WIKI_PARALLEL_COUNT` | `5` | 并行 wiki 生成任务数 |
| `WIKI_MAX_CONCURRENT_GENERATIONS` | `1` | 集群同时生成的仓库 Wiki 数量，多实例共享 |
| `WIKI_LANGUAGES` | `en,zh,zh-tw,ja,ko,es,fr,de,pt-br,pl,ru,ar` | 支持的语言（逗号分隔） |
| `SITE_URL` | `http://localhost:8090` | 公开站点 URL，用于 sitemap、robots.txt、canonical URL 和社交分享元数据 |
| `SITEMAP_REVALIDATE_SECONDS` | `3600` | sitemap 缓存 TTL（秒） |
| `LOCAL_IMPORT_ROOT` | — | 允许导入的本地目录根路径（本地目录导入白名单） |
| `MCP_ENABLED` | `true` | 是否启用 MCP 端点 |
| `GRAPHIFY_*` 系列 | — | Graphify 图谱产物配置（Backend、Model、OpenAI 凭证等） |

<Callout type="warn">
  `JWT_SECRET_KEY` 没有可用的默认值：Production 环境中缺失、过短或等于内置密钥时，应用启动失败并以退出码 1 结束。
  升级到本版本后的第一次启动会改用 `JWT_SECRET_KEY` 签名（旧版本忽略该变量），所有现有登录会话失效一次，用户需要重新登录。
</Callout>

## 数据持久化

后端将所有数据存储在映射到 `./data` 的 Docker 卷中：

```yaml
volumes:
  - ./data:/data
```

此目录包含：
- SQLite 数据库文件（使用 SQLite 时）
- 用于分析的克隆仓库文件
- 生成的文档数据
- Data Protection 密钥环 `./data/dataprotection-keys`（两个 compose 文件和 Sealos 模板都把 `DataProtection__KeyRingPath` 设为 `/data/dataprotection-keys`）

<Callout type="warn">
  定期备份 `./data` 目录。它包含所有生成的文档和仓库数据。密钥环必须与数据库一起备份和恢复，见下文 [Git connection secrets](#git-connection-secrets)。
</Callout>

## 健康检查

后端内置健康检查端点 `/health`。`compose.yaml` 和 `compose.pgsql.yaml` 都为后端配置了同样的健康检查，`web` 在后端 `service_healthy` 后才启动：

```yaml
healthcheck:
  test: ["CMD-SHELL", "curl -f http://localhost:8080/health || exit 1"]
  interval: 30s
  timeout: 10s
  retries: 3
  start_period: 15s
```

PostgreSQL 编排中，后端另外在数据库 `service_healthy` 后才启动。Sealos 模板对 `/health` 配置了存活和就绪探针。

## Git connection secrets

Shared Git connections keep one provider token each. The application protects the token with ASP.NET Core Data Protection
before it saves it in the database table `GitConnections`. The key ring is a set of XML files in
`DataProtection__KeyRingPath`. The files are plain XML protected only by file permissions. The database alone cannot
decrypt a token, and the key ring alone holds no token.

### What you must keep

- Keep `DataProtection__KeyRingPath` on a persistent volume. In the compose files and the Sealos template it is
  `/data/dataprotection-keys`, inside the `/data` volume. In Production the application does not start without it.
- Back up the database and the key ring together, and restore them together. A database restored without its key ring
  gives the error `CONNECTION_SECRET_UNREADABLE` for every connection, and no repository falls back to an old password.
  The fix is to restore the matching key ring, or to replace the token of each connection in the workspace.
- Keep the key ring when you roll the application back to an older version.
- Set `JWT_SECRET_KEY` to a random value of at least 32 bytes. Keep it as stable as the key ring, because a new value
  signs every user out.

For SQLite, use the online backup and not a file copy, because the database can be in WAL mode:

```bash
sqlite3 data/opendeepwiki.db ".backup 'backups/opendeepwiki.db'"
cp -a data/dataprotection-keys backups/dataprotection-keys
```

For PostgreSQL, use `pg_dump` for the database and copy the same key ring directory.

### Upgrade

1. Back up the database and the key ring as above.
2. Set `JWT_SECRET_KEY` in `.env`. Pull or build the new images and run `docker compose up -d`. The schema upgrade runs
   when the application starts.
3. Run the smoke checks below.
4. Expect one sign-in for every user, because the signing key changes on the first start.

A fatal start-up error (for example a missing key ring path in Production) stops the process with exit code 1 and
`docker compose logs opendeepwiki` shows the reason. The message never contains a key value.

If repositories hold old plaintext Git passwords, read [Legacy credential migration](/docs/deployment/legacy-credential-migration).
The contract step of that page is not active in this release.

### Smoke checks

```bash
docker compose ps                          # opendeepwiki shows "healthy"
curl --fail http://localhost:18081/health  # compose.pgsql.yaml: port 8080
curl --fail http://localhost:8090/         # compose.pgsql.yaml: port 3000
ls data/dataprotection-keys/*.xml          # at least one key file exists
docker compose restart opendeepwiki
curl --fail http://localhost:18081/health  # the key file names do not change after the restart
```

After a restart, an existing connection must still list its repositories. If it does not, check the key ring path first.

## 构建镜像

```bash
# 构建所有镜像
docker compose build

# 为特定架构构建（通过 Makefile）
make build-arm   # ARM64：Apple Silicon、AWS Graviton
make build-amd   # AMD64：Intel/AMD x86_64

# 构建单个服务
docker compose build opendeepwiki   # 仅后端
docker compose build web            # 仅前端
```

## 常见操作

```bash
# 后台启动
docker compose up -d

# 查看日志
docker compose logs -f

# 查看特定服务的日志
docker compose logs -f opendeepwiki

# 重启服务
docker compose restart

# 停止服务
docker compose down
```

## 故障排除

### 后端启动失败

- 验证 AI API 密钥有效且端点可达
- 检查 `CONNECTION_STRING` 与你的数据库类型匹配
- 查看日志：`docker compose logs opendeepwiki`

### 前端显示连接错误

- 确保后端已启动：`docker compose ps`
- `API_PROXY_URL` 必须指向后端容器：`http://opendeepwiki:8080`

### 磁盘空间不足

- 克隆的仓库存储在 `./data` 中。通过 web UI 或 API 清理旧仓库
- 对于大型部署，考虑从 SQLite 切换到 [PostgreSQL](/docs/deployment/database)（可直接使用 `compose.pgsql.yaml`）
